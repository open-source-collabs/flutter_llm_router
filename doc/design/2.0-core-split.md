# Design: 2.0 core split

Status: proposed. Nothing in this document is implemented.

## Goal

Split the package in two:

- **`llm_router_core`**: pure Dart. Adapters, models, routing policies, the routing loop, and cost tracking. Usable in servers, CLIs, Dart Frog, Serverpod, and Flutter apps that don't use Flutter AI Toolkit.
- **`flutter_llm_router`**: the Flutter AI Toolkit binding. `RouterLlmProvider`, `ValueListenable` bridges, and `RouterInspector`.

Why:

- The routing engine is useful outside Flutter. Today it can't be used there, because the package depends on Flutter and `flutter_ai_toolkit`.
- The 10 missing pub points come from WASM compatibility, through `flutter_ai_toolkit` and its `firebase_ai` dependency. A core package without those dependencies is expected to reach 160/160. That is an expectation, not a guarantee: pana's rules may change, and every remaining dependency must also be WASM-ready.
- A backend proxy, which the docs recommend for production, could then run the same router on the server.

## Prerequisite

Commit and release the 1.x work first (currently the unreleased 1.2.0). The split moves almost every file. Mixing that move with the 1.x feature diff would make both unreviewable, and leave users with no stable 1.x line to stay on.

## Package names

As of 2026-11-02, the pub.dev API returned 404 for both `llm_router` and `llm_router_core`, so both are unclaimed.

Recommendation: **`llm_router_core`**. It says what it is, pairs with `flutter_llm_router`, and leaves `llm_router` free for a possible umbrella package later. Claim it with a first manual publish as soon as the decision is made; names are first come, first served.

`flutter_llm_router` depends on `llm_router_core` with a version constraint, and a workspace path during development.

## Core API

### `LlmRouter`

The routing loop moves out of `RouterLlmProvider` into a core class:

```dart
class LlmRouter {
  LlmRouter({
    required List<ProviderConfig> providers,
    CostTracker? costTracker,
    Map<String, BaseLlmAdapter>? customAdapters,
    ConnectivityChecker? connectivityChecker,
    GenerationSettings settings,
    RetryPolicy retryPolicy,
    CircuitBreakerPolicy? circuitBreaker,
    RoutingStrategy routingStrategy,
    BudgetPolicy? budget,
    ResponseCache? responseCache,
    bool redactEventErrors,
    List<RouterTool> tools,
    int maxToolRounds,
  });

  Stream<String> stream(List<ChatTurn> messages);
  Future<T> generateObject<T>(List<ChatTurn> messages, {required ResponseSchema schema, required T Function(Object?) decode});

  List<AttemptLog> get lastAttemptLogs;
  Stream<List<AttemptLog>> get attemptLogChanges;
  Map<String, ProviderHealth> get providerHealth;
  Stream<Map<String, ProviderHealth>> get providerHealthChanges;
  Stream<RouterEvent> get events;

  void resetCircuits();
  void dispose();
}
```

Core works in `ChatTurn` and `TurnAttachment`, which are already toolkit-free. History stays out of core: it belongs to the chat UI.

### Change notification

Core can't use `ValueNotifier`. Each listenable becomes a synchronous getter for the current value plus a broadcast `Stream` of changes. `CostTracker` gets `totalCost` and `Stream<double> totalCostChanges`.

## Flutter package API

`RouterLlmProvider` becomes a thin `LlmProvider` around an `LlmRouter`:

- It keeps its constructor parameters and passes them through.
- It keeps `history`, converting `ChatMessage` and toolkit `Attachment` to `ChatTurn` and `TurnAttachment`, as it does now.
- `attemptLogs` and `providerHealth` stay `ValueListenable`s, backed by `ValueNotifier`s that follow the core streams.
- It exposes the engine as `router.engine` for code that needs core-only features.

For cost tracking, the Flutter package keeps a `totalCostNotifier` `ValueListenable`. Two options:

1. A `FlutterCostTracker` subclass of the core tracker that adds `totalCostNotifier`. `RouterLlmProvider` creates one by default. Most code compiles unchanged.
2. An extension that adapts the stream to a `ValueListenable`. This is more breaking, because `totalCostNotifier` stops being a member.

Recommendation: option 1.

The goal: an app that imports `package:flutter_llm_router/flutter_llm_router.dart` and uses `RouterLlmProvider`, `ProviderConfig`, `CostTracker.totalCostNotifier`, and `RouterInspector` compiles without changes, or with mechanical ones.

## Breaking changes

- `RouterLlmProvider.getDocumentEmbedding` and `getQueryEmbedding` are removed. They are deprecated in 1.x.
- `CostTracker` in core has no `totalCostNotifier`. Apps that construct `CostTracker()` themselves and bind to the notifier must use `FlutterCostTracker`.
- Custom adapters import from `package:llm_router_core/llm_router_core.dart`. The Flutter package re-exports it, so most imports keep working.
- `ProviderHealthRegistry` is internal today. It stays internal; `ProviderHealth` snapshots and change streams are the public surface.
- Using a core `CostTracker` after `dispose` throws `StateError` instead of the debug-build `FlutterError`.
- The minimum SDK may rise to support pub workspaces (Dart 3.6). The current floor is 3.8, so this is likely not a change.
- Adapter contracts move to a parts-based message model only if that is still wanted. It is a separate decision. Doing it in the same release multiplies the migration work for custom adapter authors.

## Migration guide outline

1. Who is affected: apps that only use `RouterLlmProvider` with built-in adapters (little or nothing to do), apps with custom adapters, server code.
2. Update `pubspec.yaml`: `flutter_llm_router: ^2.0.0`, or `llm_router_core: ^2.0.0` for pure Dart.
3. Removed APIs and their replacements.
4. `CostTracker` and `FlutterCostTracker`.
5. Custom adapters: the import path, otherwise unchanged.
6. Using `LlmRouter` on a server, with a minimal example.
7. FAQ: why two packages, and which one to depend on.

## CI and publishing

- CI runs analyze, format, and test per package. Coverage stays at or above 90% per package.
- Each package gets its own tag pattern, for example `llm_router_core-v2.0.0` and `flutter_llm_router-v2.0.0`, and its own publish workflow job.
- pub.dev automated publishing must be enabled per package in the pub.dev admin page, with the matching tag pattern.
- **The first publish of `llm_router_core` must be manual**, by the maintainer, with `dart pub publish`. Automated publishing can only be configured for a package that already exists.
- Publish order: core first, then the Flutter package that depends on it.
- The `pana` check runs for both. The core package should show 160/160. The Flutter package will still lose the WASM points while `flutter_ai_toolkit` pulls in `firebase_ai`.

## Execution order

1. Commit, tag, and release the 1.x line.
2. Publish a placeholder `llm_router_core` 0.0.1, or the real 2.0.0-dev.1, to claim the name. Manual.
3. Create the workspace and move pure-Dart files into `packages/llm_router_core` with `git mv`, so history follows. No code changes in this commit.
4. Replace `foundation` uses in `response_cache.dart`, `provider_health.dart`, and `cost_tracker.dart` with `package:meta` and streams. Add core tests.
5. Extract `LlmRouter` from `RouterLlmProvider`. Move the routing tests to core, unchanged except for the entry point. They are the safety net.
6. Rebuild `RouterLlmProvider`, `FlutterCostTracker`, and the `ValueListenable` bridges on top. Keep the existing router tests in the Flutter package passing.
7. Remove the deprecated embedding stubs.
8. Update the example, docs, and README for both packages. Write the migration guide.
9. Publish 2.0.0-dev.1 of both, and ask early users to try it.
10. Configure automated publishing for core, then release 2.0.0.
